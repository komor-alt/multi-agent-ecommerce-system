## 不能省略的失败与修复过程

1. 首轮 5 RPS、300 次请求的 HTTP/结果检查全部成功，P95 72.50ms；但原 Outbox 批量 50、扫描间隔 1000ms 跟不上事件产生速度。一次停机前检查仍有 2076 条待投递，最老等待 81 秒。因此补上队列恢复门禁，将可配置默认值调为批量 200、扫描 250ms。配置变化只是本地容量调优，不是对所有数据库/消息平台的通用最优值。
2. 调优后的第一轮 20 RPS：1199 次请求中成功 1198 次，压测端漏发 1 次，严格验收不通过。随后将压测 VU 预分配提高到 20；另一轮 30 秒诊断仍看到两次 retention 502 和一次过载 429，没有把这些结果删掉或算成全部成功。
3. 源码与确定性测试定位了 Runtime 快照竞争：线程 A 已向产物集合发布 Artifact，但还没更新 Task 的 artifactIds；线程 B 可以组合出前后不一致的快照，触发持久化来源校验失败。任务终态与完成时间也存在类似发布窗口。
4. 修复为 **同一 Run 的短锁保护全部生命周期修改和完整快照**。数据库、模型和工具调用不在锁内，其他 Run 使用自己的锁；不是把整个多 Agent 执行改成串行。
5. 新增 latch 回归测试，在发布第一个 Artifact 后暂停写线程，验证快照必须等待完整发布；另外验证终态取消、完成时间以及另一 Run 不受阻。修复后上述最终 20 RPS 复测通过。

这些探索轮次的流量/VU/代码版本并不完全相同，因此不据此计算“整体性能提升 X%”或声称多 Agent 比单 Agent 更优。

## 上线结论

本轮证明了离线链路在上述小负载下可完成任务、满足硬约束并排空后台投递，同时补上权限、失败收口、短事务租约、缓存界限、跨实例事件追读和监控基础。
