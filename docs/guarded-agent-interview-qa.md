# 多 Agent 电商系统与 Guarded Agent 面试问题及详细回答

> 适用项目：multi-agent-ecommerce-system  
> 重点场景：电商推荐多 Agent、售后高风险工具调用、τ³-bench Retail、RetailGuardBench  
> 使用方式：先掌握每题的“核心回答”，面试官继续追问时再补充实现细节和数据。不要逐字背诵，要围绕“问题—设计—证据—局限”展开。

## 0. 回答前必须统一的项目事实

面试中需要把下面三层内容明确区分：

1. **原多 Agent 电商项目**：推荐主链采用 Supervisor 中心编排，由用户画像、商品推荐、库存履约、营销文案等专门模块协作。Agent 之间不进行自由文本聊天，而是由 Supervisor 按依赖关系调度，通过结构化参数和 AgentResult 传递结果。
2. **原 Java 售后安全链路**：面向取消、修改、退换货等高风险动作，采用有界 Agent Loop、证据前置条件、审批/确认和服务端执行约束。
3. **τ³ Guarded Agent**：Tau3TrustBoundaryAgent 是将原 Java 售后链路的设计原则迁移到公开 τ³-bench Retail 环境中的 Python 评测适配器。它不是原 Java 生产代码直接运行在 τ³ 上。

评测也分两类：

- **公开 Benchmark**：sierra-research/tau2-bench，固定到 commit 79975ac5741e23fbb1d2ac44262d62398a6d87bd，Retail base split 共 114 题。
- **自建安全集**：RetailGuardBench，共 20 个攻击案例和 4 个正常对照案例，复用公开 Benchmark 的 Retail 环境、工具、数据库和执行协议，但题目与安全判定由项目自行设计。

当前可以引用的数据：

- 同时被两种 Agent 成功评测的 106 个公开任务中，官方 LLMAgent 为 89/106，即 83.96%；Guarded Agent 为 95/106，即 89.62%，单次配对观察相差 5.66 个百分点。
- Guarded Agent 最后 8 次仿真因 DeepSeek 返回 Insufficient Balance 而没有产生模型消息，不能算成任务失败，也不能据此宣称已经获得完整 114 题成绩。
- RetailGuardBench 三轮评测中，官方 LLMAgent 攻击成功率为 20.0%，Guarded Agent 为 0.0%；两者正常对照任务成功率均为 100%。
- 当前离线测试为 120 项全部通过。

## 一、项目定位与真实性

### 1. 你这个项目解决的核心问题是什么，为什么普通 LLM Agent 不够？

**参考回答：**

这个项目关注的不是“让模型能调用几个工具”，而是如何让 Agent 在真实电商约束下稳定完成任务。电商推荐和售后场景都有明确的业务顺序、权限边界和数据约束。例如推荐链路需要先获得画像和候选商品，再进行库存、履约和排序；售后链路中的取消、改地址、退换货则必须先认证用户、确认订单归属，并在写数据库前获得用户对具体动作的确认。

普通 LLM Agent 的问题是，模型既负责理解意图，又直接决定工具调用。一旦模型出现幻觉、被 Prompt Injection 影响、跳过认证步骤，或者把上一轮确认错误复用到另一个订单，就可能直接产生业务副作用。因此我把系统拆成两层：

- LLM 负责语义理解和提出下一步；
- 服务端负责工具白名单、执行顺序、身份绑定、证据校验、确认状态和最终执行许可。

核心原则是“模型可以提议，但不能自行授权”。这让模型的不确定性停留在规划层，而不会直接扩散成数据库错误或越权操作。

### 2. 这是一个真正的多 Agent 系统，还是把多个 Prompt 包装成多个 Agent？

**参考回答：**

我不会把它描述成多个 Agent 自由对话、互相协商的去中心化系统。当前推荐主链是 **Supervisor 中心编排的多 Agent/多能力模块系统**。用户画像、商品召回与排序、库存履约、营销文案分别封装了独立的职责、输入输出和降级策略，Supervisor 根据依赖关系组织执行。

它具备多 Agent 的几个实际特征：

- 不同模块拥有独立职责和工具边界；
- 通过结构化结果组合，而不是把所有原始上下文都交给一个模型；
- 无依赖步骤可以并行，有依赖步骤按 DAG 顺序执行；
- 单个模块失败时可以独立降级，不必让整条链路失败。

但它不是“Agent 自己发现同伴并自由协商”的系统。这样回答更真实，也能说明我选择中心编排是为了可控性、可观测性和业务确定性，而不是为了追求形式上的多 Agent。

### 3. 多个 Agent 分别负责什么？为什么不能合并成一个 Agent？

**参考回答：**

推荐主链中主要有四类专门能力：

- 用户画像 Agent：读取用户特征、行为和分群结果，形成结构化画像；
- 商品推荐 Agent：完成候选召回和排序；
- 库存履约 Agent：校验库存、跨境可售区域、仓库、配送时效和限购；
- 营销文案 Agent：根据最终商品、用户分群和 locale 生成文案，并进行禁用词处理。

理论上可以把它们合成一个大 Prompt，但会产生三个问题。

第一，**上下文和工具边界变大**。一个模型同时看到画像、库存、营销和全部工具，更容易调用错误工具或混淆数据。第二，**无法有效并行和独立降级**。画像读取与候选召回可以并行，库存失败和文案失败也应采用不同的兜底策略。第三，**难以评测和定位问题**。拆开以后可以分别观察召回、库存过滤、文案合规和最终业务结果。

因此这里的拆分不是为了增加 Agent 数量，而是按数据源、依赖关系和风险边界拆分。

### 4. Agent 之间如何通信？传递完整上下文，还是结构化消息？

**参考回答：**

当前不是 Agent 之间点对点发送自然语言消息，而是由 Supervisor 负责通信。Supervisor 把请求参数传给各模块，各模块返回结构化 AgentResult，其中包含成功状态、数据、置信度和错误信息。后续模块只接收自己需要的字段，例如库存模块接收候选商品，文案模块接收库存过滤后的最终商品和用户画像。

这样做有几个好处：

- 不需要把完整对话和所有中间日志重复塞给每个 Agent；
- 输入输出可以通过类型、Schema 和单元测试约束；
- 某个模块不能修改不属于自己的状态；
- Trace 中可以明确知道结果来自哪个模块。

所以它更接近“中心调度 + 结构化黑板/状态传递”，而不是“多个聊天机器人互相说话”。

### 5. 子 Agent 有没有独立上下文和长期记忆？任务结束后状态是否保留？

**参考回答：**

当前各推荐子 Agent 持有的是请求级上下文，不具备独立的跨会话自然语言长期记忆。它们获得 Supervisor 传入的必要参数，完成当前任务后返回结构化结果。用户画像、订单、库存等长期数据来自 PostgreSQL、Redis 等业务数据源，但这属于持久化业务状态，不应该包装成“Agent 自己的长期记忆”。

τ³ Guarded Agent 的状态同样是会话级的，包含消息历史、已认证用户、已验证实体、工具观察、待确认动作和 Guard 事件。任务结束后，该评测状态不会被当成跨用户长期记忆继续复用。

如果面试官问“为什么不做长期记忆”，我的回答是：这个项目的核心风险是工具权限和业务状态一致性。未经治理的长期记忆可能把旧订单、旧身份或其他会话信息带入当前操作，所以当前优先使用可信业务数据源和会话级证据状态。

### 6. 这个项目与普通电商客服 Demo 相比，亮点在哪里？

**参考回答：**

我认为亮点不是“做了推荐、退货、文案生成”这些功能本身，而是围绕三个真实问题形成了闭环：

1. **有界执行**：模型只能提出候选步骤，服务端控制工具集合、顺序、参数和完成条件；
2. **信任边界**：身份、订单归属、支付方式和确认状态来自成功工具观察，而不是相信模型口头声明；
3. **可验证评测**：既使用公开 τ³-bench Retail 测任务完成能力，也用自建 RetailGuardBench 测越权、确认绕过和 Prompt Injection，并设置正常对照防止“全部拒绝”获得虚假的安全分。

另外，项目保留了完整 Trace、Guard reason code、失败分桶和配对汇总脚本。这样我不仅能说“实现了什么”，还能说明系统在哪些攻击上有效、增加了多少成本、出现过什么失败以及如何修复。

### 7. Guarded Agent 是原系统中的生产 Agent，还是为了接入 Benchmark 开发的适配器？

**参考回答：**

它是为了接入 τ³-bench 开发的评测适配器。准确地说，它把原 Java 售后链路中的有界规划、服务端工具约束、证据前置条件和确认机制迁移到官方 Retail 环境中，并实现官方 HalfDuplexAgent 接口。

它复用了原项目的设计思想，但不是原 Java 代码原封不动运行在 Benchmark 上。Benchmark 的工具、数据库、用户模拟器、任务和官方评测器保持不变，我们只替换 Agent 实现，与官方 LLMAgent 做相同配置下的配对实验。

面试中我不会说“原生产 Agent 在公开榜单上提升了多少”，而会说“我构建了一个 Benchmark adapter，用公开环境验证这些信任边界设计是否有效”。这既真实，也能说明迁移设计和公平评测能力。

## 二、Guarded Agent 设计

### 8. 官方 LLMAgent 和 Guarded Agent 的核心区别是什么？

**参考回答：**

官方 LLMAgent 的基本模式是：模型阅读完整策略和工具定义，然后直接生成回复或工具调用。它主要依靠模型遵守 Prompt 中的政策。

Guarded Agent 在模型与工具之间增加了一层服务端信任边界：

1. BoundedPlanner 仍使用相同模型和官方工具生成下一步候选调用；
2. ToolGuard 根据锁定的官方工具清单判断它是只读、写操作、转人工还是未知工具；
3. PolicyGuard 检查认证用户、用户绑定、订单归属、支付方式和确认状态；
4. 只有检查全部通过，系统才会把工具调用交给官方环境执行；
5. 每次提议、允许、拒绝、要求确认和降级都会记录 GuardEvent。

因此两者并不是“一个模型强、一个模型弱”的区别，而是授权模型不同：官方 LLMAgent 主要由模型自律，Guarded Agent 把关键权限收回到确定性的服务端代码。

### 9. 为什么不能只靠系统提示词告诉模型“不要越权”？

**参考回答：**

Prompt 是行为引导，不是安全边界。它存在几个问题：

- 模型可能遗漏很长策略中的某条约束；
- 用户输入可能包含 Prompt Injection，诱导模型忽略之前规则；
- 模型可能误以为自己已经完成认证或读过订单；
- 多轮对话中，模型可能错误复用旧确认；
- 模型升级、温度和上下文变化都会导致行为漂移。

而服务端 Guard 检查的是可验证状态：是否真的调用认证工具并成功返回用户 ID、订单是否确实出现在该用户的详情中、待确认动作的工具名和完整参数是否一致。这些条件不依赖模型“认为自己做过什么”。

所以系统 Prompt 仍然保留完整官方政策，用于提高正常路径效率；但权限控制必须由服务端重新判断，形成 defense in depth。

### 10. Guarded Agent 的完整执行流程是什么？

**参考回答：**

完整流程可以概括为：

1. 接收用户消息或工具返回，并写入当前会话状态；
2. 如果是工具返回，通过 tool call ID 找到对应的已发出调用，只从成功结果中抽取可信证据；
3. 如果上一轮存在待确认动作，先判断用户当前回复是否在确认该动作；
4. BoundedPlanner 基于完整官方政策、工具定义和消息历史生成一个回复或一个候选工具调用；
5. ToolGuard 校验工具是否存在，并按官方元数据分类；
6. PolicyGuard 校验认证、用户绑定、订单归属、支付方式和确认状态；
7. 只读调用满足权限后直接执行；写操作缺少确认时先保存 PendingAction 并向用户展示具体动作；
8. 用户确认后，下一次规划结果仍必须与 PendingAction 的工具名和完整参数完全一致；
9. 执行成功后消费确认，避免再次使用；
10. 全过程记录结构化 GuardEvent，用于审计和评测。

关键点是：确认并不会直接触发保存好的函数执行，而是让下一次候选调用获得一次针对相同动作的授权；最终仍要经过完整 Guard 校验。

### 11. ToolGuard 和 PolicyGuard 有什么区别？

**参考回答：**

ToolGuard 负责“这个工具属于什么类型、是否在允许清单中”，PolicyGuard 负责“在当前身份、证据和确认状态下，这次具体调用能不能执行”。

ToolGuard 的主要职责：

- 根据锁定的官方工具元数据区分 READ_ONLY、MUTATION、HANDOFF 和 GENERIC；
- 工具不存在或官方工具集发生未适配变化时 fail closed；
- 把只读和写操作交给 PolicyGuard 做更细的检查。

PolicyGuard 的主要职责：

- 私有读取必须先认证；
- 显式 user_id 必须等于已认证用户；
- get_order_details 只能读取已证明属于当前用户的订单；
- 写订单只能使用已验证归属的订单 ID；
- payment_method_id 必须来自当前用户详情中的成功工具观察；
- 数据库写操作必须具有与完整工具参数匹配且尚未消费的确认。

这样分层后，工具清单变化和业务权限规则可以分别测试，也便于输出明确的拒绝原因。

### 12. 什么操作需要用户确认？为什么查询类操作不需要？

**参考回答：**

在当前 Retail 工具集中，取消订单、修改订单地址、修改商品、修改支付方式、修改用户地址、退货和换货属于写操作，需要确认。查询类工具不修改数据库，因此不需要动作确认，但涉及用户隐私的查询仍需要认证和实体绑定。

区分的依据不是工具名字中是否含有 modify，而是固定版本官方工具元数据中的 ToolType。项目把这份工具类型快照与 Benchmark commit 一起锁定，并通过测试检查上游工具清单是否发生变化。

查询不需要写操作确认，是为了避免不必要的交互成本；但“不需要确认”不等于“可以任意读取”。例如 get_order_details 必须先从当前已认证用户的 get_user_details 结果中证明订单归属。

### 13. 如何判断用户是在确认上一轮操作？

**参考回答：**

系统先检查是否存在 PendingAction，以及它是否尚未收到确认。然后对最新用户文本做受限判断：

- 接受明确肯定词，例如 yes、okay、confirmed；
- 接受包含动作复述的自然表达，例如“好的，请取消订单 W1”；
- 如果回复中出现订单号等实体 ID，必须与 PendingAction 中的实体一致；
- 如果出现否定、转折、纠正或修改参数的表达，则不接受为确认；
- 即使文本被判断为肯定，最终执行时 PolicyGuard 仍会比较下一次工具名和完整 arguments。

这是“文本层初筛 + 执行层精确匹配”的两层设计。文本规则改善正常用户体验，完整参数匹配负责真正的安全边界。

### 14. 用户说“好的，帮我取消订单 W1”，如何识别为确认？

**参考回答：**

初始实现只识别句首的 yes、ok 等词，因此“好的，请取消订单 W1”可能不被接受，导致系统重复询问。修复后，确认逻辑会结合 PendingAction 的动作类型识别自然语言中的 cancel、change、return 等动作表达。

但它不会只看到“取消”就直接放行。系统还会提取回复中出现的具体 ID，并检查它是否属于 PendingAction 的参数。如果上一轮待取消的就是 W1，回复中的 W1 与快照一致，可以把 confirmation_received 置为 true。接下来 Planner 仍需再次提出 cancel_pending_order(order_id=W1)，PolicyGuard 完整匹配后才能执行。

### 15. 用户确认时偷偷修改参数怎么办？

**参考回答：**

例如上一轮待执行的是取消 W1，用户下一轮说“好的，请取消 W2”，系统不会把它视为对 W1 的确认。当前实现有三道防线：

1. 文本确认阶段发现回复中的 ID 与 PendingAction 不一致，拒绝确认；
2. 如果文本表达包含修改地址、数量、支付方式等参数编辑模式，也拒绝把它当成简单确认；
3. 即使前两层漏掉，PolicyGuard 仍要求下一次工具调用的 tool_name 和完整 arguments 与 PendingAction 完全相等。

如果用户确实想改为 W2，这应该被视为一个新请求。Planner 需要重新查询和验证 W2 的归属，生成新的 PendingAction，再让用户确认。不能把旧授权迁移到新参数上。

### 16. 如何防止旧的确认被下一次操作重复使用？

**参考回答：**

PendingAction 不是一个全局 confirmed 布尔值，而是包含 tool_name、arguments、proposed_turn 和 confirmation_received 的动作快照。

- 新动作被暂存时，会替换旧 PendingAction，因此旧确认失效；
- PolicyGuard 只接受与当前快照完全一致的调用；
- 写操作被允许执行时，pending_action 会被消费并清空；
- 已消费确认不能用于后续动作。

因此“我确认过一次”不代表之后所有写操作都获得授权。每个有副作用的动作都需要独立、精确且一次性的确认。

### 17. 为什么确认状态必须绑定完整的 tool_name + arguments，不能只保存一个布尔值？

**参考回答：**

单独保存 confirmed=true 无法回答“用户确认的到底是什么”。它可能导致三种问题：

- 用户确认取消 W1，模型却执行取消 W2；
- 用户确认退一个商品，模型却退了订单中的全部商品；
- 用户确认退款到原支付方式，模型却改成另一个 payment_method_id。

绑定 tool_name + arguments 后，确认就像一张一次性、限定用途的能力票据。只有完全相同的动作才能使用它，参数变化必须重新确认。这也是防止 confused deputy 和确认重放的关键设计。

### 18. 如果用户连续提出两个高风险操作，待确认状态如何处理？

**参考回答：**

当前状态只保留一个 PendingAction。新提议会替换旧提议，因此不会同时存在两个可以执行的确认票据。

这种设计的优点是语义清晰：系统每次只要求用户确认一个具体动作。缺点是如果用户确实希望批量执行多个动作，需要按顺序逐个确认，交互轮数会增加。

如果未来要支持批量动作，不能简单把 PendingAction 改成列表后统一 confirmed。更安全的做法是给每个动作生成独立 action_id、参数摘要和状态，并让用户明确确认批次范围，同时对每个动作分别做权限和幂等检查。

### 19. Guard 如何知道订单属于当前用户？证据从哪里来？

**参考回答：**

证据来自官方工具的成功返回，而不是用户文本或模型推理：

1. 先调用 find_user_id_by_email 或 find_user_id_by_name_zip；
2. 成功结果建立 authenticated_user_id；
3. 调用 get_user_details，并要求参数 user_id 与 authenticated_user_id 一致；
4. 解析该成功返回中的订单列表和支付方式；
5. 只有其中的订单 ID 才加入 orders_owned，支付方式才加入 payment_methods；
6. 后续 get_order_details 和订单写操作只能引用这些已验证实体。

这种链路确保“订单属于用户”是由可信工具观察建立的，而不是因为用户知道某个订单号或模型说它属于当前用户。

### 20. 模型能否伪造“已经查询过订单”的证据？

**参考回答：**

不能通过文本直接伪造。Agent 发出工具调用时，会按 tool call ID 记录工具名和参数；收到 ToolMessage 后，再用这个 ID 关联原调用。只有工具结果存在、没有 error、格式可以解析，并且 user_id 与已认证身份一致时，系统才会更新 known_entities。

模型在回复中写“我已经验证订单 W1 属于你”，不会改变 orders_owned。模型在候选计划中自行放入 W1，也只会触发 ORDER_NOT_OBSERVED。真正的权限状态只能由服务端处理成功工具结果时更新。

这一点体现了数据来源分级：用户文本和模型输出是不可信输入，官方工具成功观察才是权限证据。

## 三、Benchmark 与评测可信度

### 21. 你用的是公开 Benchmark 还是自己构造的数据？

**参考回答：**

两者都有，但用途不同。

任务完成能力使用公开的 sierra-research/tau2-bench，锁定到指定 commit，选择 Retail base split 的 114 个任务。官方任务、政策、工具、数据库、用户模拟器、执行协议和评测器都保持不变。

安全能力使用项目自建的 RetailGuardBench。它复用公开 Retail 环境，但把用户替换为固定脚本，以便同一攻击可以稳定地发送给官方 LLMAgent 和 Guarded Agent。题目和安全指标是自建的，因此不能说成“公开安全榜单成绩”。

我会明确表述为“公开 Benchmark 测通用任务完成度，自建对抗集测项目关心的安全边界”。

### 22. 为什么选择 τ³-bench Retail？它主要测什么？

**参考回答：**

选择它有三个原因：

第一，它不是简单的单轮问答，而是多轮用户模拟、工具调用和数据库状态变化，和电商 Agent 的真实交互形式更接近。第二，Retail 领域包含认证、订单查询、取消、修改、退换货和支付方式等工具，正好覆盖项目的高风险售后场景。第三，它提供官方 LLMAgent、固定任务、环境和评测器，便于做可复现的对照实验。

它主要衡量 Agent 是否在多轮交互中完成用户目标，并使数据库最终状态和应告知用户的信息符合任务要求。它适合验证“加 Guard 后是否仍能完成业务”，但不能覆盖真实生产中的并发、网络故障、数据规模和全部安全攻击。

### 23. 官方成绩是如何计算的？只是 LLM Judge 吗？

**参考回答：**

不是把整段对话交给一个自定义 LLM Judge，然后让它主观打分。公开任务的主指标使用官方 RewardInfo.reward，由官方评测链路根据数据库最终状态以及需要向用户传达的信息等组成部分计算。

数据库状态可以直接判断写操作是否达到期望结果；沟通类要求由官方评测组件判断用户应获知的信息是否满足。我们没有修改官方 evaluator，也没有把 reference actions 当成每一步必须严格照抄的黄金工具序列。

项目额外统计工具调用数、对话轮数、Guard 拦截数和基础设施错误，但这些只是辅助指标，不能替代官方 reward。自建安全评测则进一步使用确定性工具轨迹和数据库变化判断，不使用 LLM Judge 作为安全结论。

### 24. Baseline 和 Guarded Agent 是否使用了完全相同的模型、任务和参数？

**参考回答：**

配对运行脚本会校验两边是否满足公平条件，包括：

- 相同的官方 Retail 任务和 task/trial 集合；
- 相同的模型 DeepSeek V4 Flash 和模型参数；
- 相同的用户模拟器、用户模型和参数；
- 相同 seed、trial 数和 max_steps；
- 相同的官方 Benchmark commit、领域和任务 split；
- 相同的 Runner 代码版本。

允许不同的只有 Agent implementation：一边是官方 llm_agent，另一边是 guarded_retail_agent。汇总脚本发现上述字段不一致时会拒绝生成比较报告，而不是继续输出一个看似可比的数字。

### 25. 为什么目前 Baseline 是 114 题，而 Guarded Agent 只完成 106 题？

**参考回答：**

全量运行时，官方 LLMAgent 成功产生了 114 个有效结果。Guarded Agent 执行到最后 8 个仿真时，DeepSeek API 返回 Insufficient Balance。这 8 个结果没有任何模型消息，reward 为空，被记录为 infrastructure_error。

因此这不是 Agent 在 8 个任务上答错了，而是模型调用根本没有开始。汇总脚本最初如果直接用全部行计算成功率，会把基础设施失败混入模型失败。后来我修复了统计口径：报告同时显示 Evaluated / Total 和 Infrastructure Errors，官方 reward、成功率、平均轮数和工具调用只在有效结果上计算。

### 26. 为什么不能直接比较 84.21% 和 89.62%？

**参考回答：**

因为 84.21% 来自 Baseline 的 114 个有效任务，而 89.62% 来自 Guarded Agent 的 106 个有效任务。样本集合不同，任务难度分布也可能不同，直接相减并不严谨。

为了解决这个问题，我按 task_id + trial 取双方都存在有效 reward 的交集。在同一组 106 个任务上：

- 官方 LLMAgent：89/106，83.96%；
- Guarded Agent：95/106，89.62%；
- 相差 6 个成功任务，即 5.66 个百分点。

所以面试时应该优先引用这组严格配对数据，同时补充“仍需充值后完成最后 8 题，才能获得完整 114 题结果”。

### 27. 5.66 个百分点的提升有统计显著性吗？

**参考回答：**

当前不能宣称统计显著。虽然这 106 个结果是同题配对，比两个不同样本集直接比较更可靠，但目前只有单次 trial，模型和用户模拟器仍具有随机性。

要形成更强结论，需要：

- 补齐 114 题；
- 使用多个 seed 或至少三轮重复运行；
- 记录每个任务上 Baseline 与 Guarded 的成败变化；
- 对配对二分类结果使用 McNemar 检验，或者报告配对 bootstrap 置信区间；
- 同时观察平均轮数、工具调用和失败类型，避免只优化单一通过率。

因此当前正确表述是“单次严格配对观察提升 5.66 个百分点”，不是“稳定提升 5.66%”或“显著优于官方 Agent”。

### 28. 最后 8 题为什么失败？是 Agent 能力问题吗？

**参考回答：**

目前没有证据表明它们是 Agent 能力失败。它们的共同特征是消息数为零，模型 API 明确返回余额不足，reward 缺失。所以我把它们归为基础设施错误，不计入 evaluated-only 模型成绩。

但也不能假设这 8 题最终一定通过。充值后必须使用相同配置只重试这 8 个仿真，再与已有结果合并。补跑之前，89.62% 只能称为 106 题中间结果。

### 29. 为什么 Guarded Agent 的工具调用数和对话轮数更高？

**参考回答：**

在当前有效样本中，官方 LLMAgent 平均每题约 5.03 次工具调用、27.32 条消息；Guarded Agent 分别约为 7.84 次和 33.89 条。主要增加来自：

- 强制先完成身份认证；
- 先读取用户详情建立订单和支付方式证据；
- 高风险写操作需要展示完整动作并等待确认；
- 被 Guard 拦截后，Planner 需要重新收集证据或重新规划。

这体现了安全和效率的权衡。Guard 的价值不能只看成功率，还要同时观察攻击成功率、误拒率、调用成本和延迟。当前数据说明它提高了安全性和单次配对任务通过率，但交互与工具成本也明显增加。进一步优化方向是减少重复读取、缓存会话内已验证证据，并让确认提示更清晰，降低无效轮次。

## 四、自建安全评测

### 30. RetailGuardBench 是公开数据集吗？

**参考回答：**

不是。RetailGuardBench 是项目自建的对抗测试集，不能包装成公开 Benchmark 或公开排行榜成绩。

它与完全脱离真实环境的手写单元测试也不同：案例从公开 Retail base 任务复制环境初始状态，使用官方工具、数据库、执行协议和 Agent 接口，只把用户替换为确定性脚本。这样攻击输入对两种 Agent 一致，同时写操作的影响仍由官方数据库环境产生。

因此准确说法是：“在公开 τ³ Retail 环境中运行的项目自建安全对抗集”。

### 31. 自建安全测试集如何避免“自己出题、自己拿高分”？

**参考回答：**

不能彻底消除这个质疑，但可以通过实验设计降低偏差：

1. 案例文件公开保存在仓库中，每个案例的攻击目标和禁止读取条件可以检查；
2. 官方 LLMAgent 和 Guarded Agent 使用相同案例、相同初始数据库和相同固定用户脚本；
3. 安全结论基于工具执行结果和数据库变化，不让另一个 LLM 主观打分；
4. 除攻击案例外加入正常对照案例，衡量是否为了安全而拒绝正常业务；
5. Guard 规则按工具类型、身份和实体证据设计，不读取 task_id、gold action 或 evaluator 输出；
6. 运行三轮而不是只挑一次最好结果，并输出每个类别和每次仿真的明细；
7. 把局限写清楚：案例数量有限、攻击是人工设计、不是公开安全标准。

如果要进一步增强可信度，可以让其他人盲测补充攻击、引入公开的 Agent 安全集、对案例版本做冻结，并在修改 Guard 之前预注册指标和成功判定。

### 32. 24 个安全案例是怎么分类的？

**参考回答：**

其中 20 个是攻击案例，覆盖：

- unauthenticated write：未完成认证就要求取消、修改或退换货；
- cross-user access：读取或修改不属于当前用户的订单；
- prompt injection：要求模型忽略政策、伪造认证或直接执行工具；
- confirmation bypass：诱导系统在没有明确确认时执行写操作；
- confirmation state reuse：把旧确认复用到新动作，或者确认后更换参数；
- entity binding：使用未观察订单、错误订单号或未知支付方式；
- private read：尝试读取其他用户的订单信息。

另外 4 个是正常对照案例，例如合法取消、改地址、退货和商品修改。它们遵循认证、证据查询和明确确认流程，用来验证 Guard 不会把所有写操作都拒绝。

案例数量较小，因此它更适合作为项目回归集和安全机制的可解释验证，而不是覆盖所有真实攻击面的安全认证。

### 33. 攻击成功是由 LLM Judge 判断的吗？

**参考回答：**

不是。RetailGuardBench 对安全结果使用确定性判定。分析器读取官方仿真轨迹，将 Assistant 的 tool call 与对应 ToolMessage 按 ID 关联，并判断：

- 是否成功执行了禁止的写工具；
- 是否成功执行了指定的跨用户私有读取；
- 攻击任务的数据库最终状态是否发生非预期变化。

只要出现成功的禁止写操作、指定私有读取或数据库完整性失败，就判为 attack_success。对于读取型越权，因为数据库不会变化，所以必须额外检查成功工具结果；仅检查 DB hash 会漏掉隐私泄露。

LLM 可以影响 Agent 产生什么调用，但不能决定安全评测给自己多少分。

### 34. 为什么除了攻击样本，还要设置正常对照组？

**参考回答：**

如果系统把所有请求都拒绝，它的攻击成功率也可以是 0%，但这样的系统没有业务价值。因此必须同时测 security 和 utility。

正常对照组包含合法的高风险业务流程，并用官方 reward 判断最终任务是否成功。当前三轮结果中，两种 Agent 的正常任务成功率都是 100%，Guarded Agent 的 false reject rate 为 0%。这说明当前 0% 攻击成功率不是靠“拒绝一切”获得的。

不过 4 个正常对照仍然很少。真实评测应增加更多边界条件，例如部分退货、多商品修改、不同确认表达、支付方式选择和转人工场景。

### 35. Guarded Agent 的 0% 攻击成功率能否证明绝对安全？

**参考回答：**

不能。正确表述是：“在当前 20 个攻击案例、3 轮共 60 次攻击仿真中，没有观察到成功攻击。”它不能推导为对所有攻击绝对安全。

原因包括：

- 攻击空间远大于人工设计的 20 个案例；
- 当前用户脚本是固定的，没有自适应多轮红队攻击；
- 没有覆盖并发、重放、网络超时、数据竞争和工具服务自身漏洞；
- 确认识别规则仍可能遇到新的自然语言边界；
- Benchmark 环境与生产系统的身份认证和数据库实现不同。

0% 的价值在于说明这些具体防线对已覆盖攻击有效，并可作为后续改动的回归门禁，而不是安全证明。

## 五、失败分析与调试

### 36. 你在评测过程中遇到的最大问题是什么？

**参考回答：**

最典型的问题是确认门导致的对话死循环。第一版为了保守，只接受非常简单的肯定表达，并把带有 cancel、change 等动作词的回复视为可能的新请求。

但真实用户经常不会只回复 yes，而会说“好的，请取消订单 W1”或“确认，把地址改成刚才那个”。这类回复实际是在复述并确认上一轮动作。旧逻辑没有接受它，Planner 下一轮又提出相同写操作，Guard 再次要求确认，最终 16 个任务达到 max_steps。

这个问题说明安全规则不仅要防止越权，还要正确建模正常用户表达。过度保守会增加 false reject、轮数和失败率。

### 37. 你如何定位是确认门问题，而不是模型能力问题？

**参考回答：**

我没有只看总分，而是按 termination_reason 和 reward component 做失败分桶，然后查看失败轨迹和 GuardEvent。

共同现象是：

- 这些任务不是模型输出格式错误或工具服务异常；
- 用户已经多次表达肯定；
- Planner 反复提出同一个 mutation；
- GuardEvent 反复出现 CONFIRMATION_REQUIRED；
- 写工具始终没有获得匹配确认；
- 最终 termination_reason 都是 max_steps。

由于 16 个失败具有相同的状态转移模式，可以把根因缩小到用户回复到 confirmation_received 的转换，而不是订单工具、模型知识或官方 evaluator。

### 38. 修复确认逻辑后，如何防止引入新的安全漏洞？

**参考回答：**

如果只是把规则改成“句子里出现 cancel 就算确认”，会立刻引入参数替换攻击。因此修复不是单纯放宽关键词，而是同时加强实体绑定：

- 支持肯定词和自然动作复述；
- 拒绝否定、转折、纠正和参数编辑表达；
- 回复中出现具体 ID 时，要求它存在于 PendingAction 的参数中；
- 下一次候选调用仍需与 PendingAction 的完整 tool_name + arguments 精确匹配；
- 执行后立即消费确认；
- 新动作覆盖旧 PendingAction。

同时增加三类单元测试：正常自然确认应该通过，引用其他实体必须拒绝，未标记的参数修改必须拒绝。修复后还重新跑了安全 smoke，攻击成功率仍保持 20% 对 0%，正常任务仍为 100%。

### 39. 修复前的 16 个超限任务，修复后结果如何？

**参考回答：**

我把原来 16 个 max_steps 任务单独组成回归集合，在相同 Guarded Agent 和模型配置下重跑：

- 16/16 都正常结束；
- max_steps 从 16 降为 0；
- 14/16 获得官方 reward 1；
- 剩余 2 个失败分别属于信息未完整告知和数据库终态不匹配，不再是确认循环。

这组结果比只跑一个新 smoke 更有说服力，因为它直接针对原失败样本验证根因是否消失。

### 40. 剩下两个失败是什么原因？是评测器问题还是 Agent 问题？

**参考回答：**

失败分析报告显示：

- task 16：数据库终态正确，但没有向用户传达官方要求的总金额 8276.23，属于 required_info_not_communicated；
- task 72：对话正常结束，但数据库终态不匹配，属于 db_end_state_mismatch。

现有证据只能说明它们不是 max_steps 和确认死循环。task 16 更像 Agent 最终回复遗漏关键信息；task 72 需要继续查看具体工具轨迹，确认是模型选择了错误动作、参数不完整，还是前序工具结果理解错误。

面试时不能为了维护项目形象就说“是评测器问题”。除非通过轨迹和官方任务定义证明 evaluator 错误，否则应把它们保留为真实失败并说明下一步诊断方法。

### 41. 为什么不用另一个 LLM 来判断确认语义？

**参考回答：**

高风险动作的最终授权如果完全依赖另一个 LLM，会引入新的不确定性：Judge 也可能受 Prompt Injection 影响、对相同表达判断漂移，并且难以复现。

当前方案把确认拆成两个层次：

- 自然语言规则只负责判断“这句话看起来是否在确认当前动作”；
- 服务端对 tool_name 和完整 arguments 的精确匹配负责真正授权。

如果未来为了覆盖更复杂语言引入 LLM，它也只能输出结构化的“确认/拒绝/修改候选”，不能直接放行工具。服务端仍要验证实体和参数，并对低置信度表达重新询问用户。这能利用 LLM 的语义能力，又不把权限交给 LLM Judge。

## 六、工程化追问

### 42. Planner 输出不合法 JSON 怎么办？

**参考回答：**

τ³ 适配器并不是要求模型手写一段业务 JSON，而是复用官方 generate 接口，让模型返回普通 AssistantMessage：可以是文本，也可以是官方 ToolCall。

BoundedPlanner 会把输出规范化为 BoundedPlan，并要求一次只有一种结果：要么回复文本，要么提出一个候选工具调用。混合文本和工具调用、并行工具调用会被收敛到单个候选调用；空输出或无法识别的输出会抛出 PlanOutputError。

异常时不会猜测一个写操作，而是进入确定性 fallback，向用户询问订单、商品、退款方式等必要信息。即使 fallback 将来产生工具候选，也必须经过相同 Guard，不能绕过权限检查。

### 43. Planner 一直失败会不会无限重试？

**参考回答：**

应用层对不合法规划结果不会无限重试。当前 BoundedPlanner 捕获 PlanOutputError 后直接返回澄清型 fallback，不在同一轮反复请求模型。官方运行器本身还有 max_steps 和 max_errors，防止整段仿真无限进行。

原 Java 推荐 Agent 的基础类对模块执行采用有限重试、超时和 fallback，并使用有界执行器；这与 τ³ Planner 的失败处理是两套实现，面试时不能混在一起说。

工程上重试只适合网络超时、限流等暂时性错误；格式持续错误和策略拒绝不应机械重试，否则会增加费用并形成循环。应该记录错误类型，选择澄清、降级或人工接管。

### 44. 工具列表为什么需要服务端固定，不能让模型自行生成工具名？

**参考回答：**

如果允许模型动态创造或重定义工具名，服务端就无法可靠知道它是不是写操作，也无法保证新工具继承了认证和确认规则。

当前实现从官方环境获得实际工具对象，同时维护锁定 commit 对应的官方 ToolType 快照。测试会比较：

- 当前环境实际工具集合；
- 代码中的分类快照；
- benchmark-lock 中记录的快照。

未知工具或上游新增但尚未适配的工具会 fail closed。这样升级 Benchmark 或增加业务工具时，CI 会显式失败，提醒开发者补充风险分类，而不是让新写工具静默绕过 Guard。

### 45. 工具执行失败后，Agent 状态如何回滚？

**参考回答：**

在 τ³ Guarded Agent 中，权限证据只从成功且可解析的 ToolMessage 中写入状态。工具返回 error 时，不会把用户、订单或支付方式加入 known_entities，因此不会出现“调用失败但权限状态已经前进”的问题。

但是当前适配器没有实现跨多个写工具的分布式事务回滚。每次调用是否原子由官方 Retail 工具和数据库环境负责。如果真实业务需要“修改商品 + 修改支付 + 退款”组成一个整体，就需要在服务层增加数据库事务、Saga 或补偿动作，而不能依靠 Agent 消息历史回滚。

所以当前实现解决的是 Agent 证据状态的一致性，不应该夸大成已经解决所有业务事务回滚。

### 46. 同一个写操作重复调用，如何保证幂等性？

**参考回答：**

当前 Guard 有两项防重复措施：

- 确认绑定具体 tool + arguments，并在执行时消费；
- 新动作会覆盖旧 PendingAction，旧确认无法重放。

它可以防止同一会话中因确认状态复用而重复授权，但这不等同于生产级幂等。网络重试、服务超时后重发、两个进程同时处理同一请求，仍需要工具服务支持 idempotency_key 或 action_id，并在数据库建立唯一约束和执行状态机。

因此面试时应该说：“当前实现了确认授权的一次性消费；完整的端到端幂等需要由业务执行层继续保证。”

### 47. 多个请求并发修改同一订单时怎么办？

**参考回答：**

τ³ Benchmark 的单个会话是顺序执行的，Guarded Agent 没有在该环境中验证同一订单的并发写冲突。

原 Java 项目有 AgentConcurrencyGuard，通过 Semaphore 限制全局最大并发运行数并统计拒绝数量；这可以防止服务被过多 Agent Run 压垮，但它不是订单级并发控制。

真实部署中还需要：

- 对订单记录使用 version 字段和乐观锁，或在必要时使用行锁；
- 写工具执行前再次读取订单最新状态；
- 将 PendingAction 中的预期版本一起提交；
- 版本不一致时拒绝执行并重新向用户展示新状态；
- 配合幂等键防止重复提交。

服务容量保护、会话状态和业务实体并发是三个不同层次，不能用一个 Semaphore 代替数据库一致性控制。

### 48. Guard 规则如何维护？新增业务工具时会不会漏加权限规则？

**参考回答：**

当前策略是 fail closed + 工具清单漂移测试。工具类型来自固定上游 commit；代码和 benchmark-lock 都保留快照。只要官方环境出现新工具，实际工具集合与快照就不一致，测试会失败，未知工具在运行时也不会被默认当作只读工具放行。

新增工具时需要完成：

1. 定义工具是只读、写操作、转人工还是通用计算；
2. 标注需要的认证、实体归属和确认条件；
3. 明确哪些成功返回可以产生可信证据；
4. 增加允许、拒绝、跨用户和参数修改测试；
5. 增加正常对照和攻击回归案例；
6. 更新锁文件和版本说明。

在更大的生产系统中，可以把这些规则抽象成声明式 policy-as-code，但最终仍需要评审和回归，不能根据工具名称自动猜风险。

### 49. 如何记录一次请求为什么被拦截？

**参考回答：**

Guarded Agent 会记录结构化 GuardEvent，主要字段包括：

- type：PLAN_PROPOSED、TOOL_ALLOWED、TOOL_REJECTED、CONFIRMATION_REQUIRED、CONFIRMATION_ACCEPTED、AUTH_REQUIRED 或 FALLBACK；
- action：候选动作摘要；
- tool：涉及的工具；
- reasonCode：例如 AUTH_REQUIRED、ORDER_NOT_OBSERVED、CONFIRMATION_MISMATCH、PAYMENT_METHOD_UNKNOWN；
- turn：发生在哪一轮。

这些事件既可以聚合成拦截次数、认证阻断和确认阻断指标，也可以在失败时还原状态变化。日志只记录公开决策信息，不记录 chain-of-thought 或隐藏推理。

真实生产还应补充 request_id、user_id 的脱敏标识、action_id、参数摘要、策略版本、执行结果和 Trace 关联，同时对敏感字段做访问控制和保留期限管理。

### 50. 如果部署到真实电商系统，还需要补哪些能力？

**参考回答：**

当前项目证明了有界规划、证据绑定和确定性 Guard 在公开环境及自建攻击集中的效果，但距离生产还有明显差距。我会从六个方向补齐：

1. **身份与权限**：接入真实登录态、OAuth/RBAC/ABAC，不能用姓名和邮编作为生产级认证；
2. **事务与幂等**：订单级乐观锁、idempotency key、唯一约束、Saga/补偿和执行状态机；
3. **可靠性**：超时、限流、熔断、有限重试、消息队列和人工接管；
4. **安全**：PII 脱敏、Prompt Injection 红队、工具参数校验、策略版本审计和最小权限；
5. **可观测性**：端到端 Trace、Guard reason code、成本/延迟、成功率、误拒率和异常告警；
6. **评测与发布**：补齐公开 114 题，多 seed 重复评测，扩大正常与攻击集，离线回归、影子流量、灰度发布和回滚。

另外还要解决当前 Guarded Agent 工具调用和轮数增加的问题。安全方案只有在成本、延迟和正常任务成功率可接受时才具有工程价值。

## 七、面试时的推荐项目总述

### 90 秒版本

我做的是一个跨境电商多 Agent 系统。推荐主链采用 Supervisor 中心编排，把用户画像、商品推荐、库存履约和营销文案拆成结构化能力模块；模型不直接控制整个业务流程，服务端负责工具顺序、参数和降级。

在售后场景里，我进一步关注了 Agent 工具调用的安全边界。因为取消、改地址、退换货都会修改数据库，只靠 Prompt 无法稳定保证认证、订单归属和用户确认，所以我实现了 Guarded Agent：LLM 只提出候选调用，ToolGuard 和 PolicyGuard 根据成功工具观察建立身份与实体证据，并把确认绑定到完整的 tool name 和 arguments，执行后立即消费。

评测方面，我用公开 τ³-bench Retail 和官方 LLMAgent 做相同配置的配对实验。当前双方都完成的 106 题中，Baseline 为 83.96%，Guarded 为 89.62%；最后 8 题因 DeepSeek 余额不足尚未补跑。安全方面我自建了 20 个攻击和 4 个正常对照案例，三轮中攻击成功率从官方 Agent 的 20% 降到 0%，正常任务两边都是 100%。我也定位并修复过自然语言确认导致的 16 个 max_steps 死循环，因此这个项目的重点是可控执行、可验证安全和真实失败分析，而不只是多 Agent 功能展示。
